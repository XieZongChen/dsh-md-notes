# 笔记作为 agent 的记忆（设计）

> 这份文档回答一个问题：**笔记到底能不能提升 dsh 的问答效果？**
> 答案是「按老设计不能，按这个设计也许能」——本文写清差别、已落地部分、以及如何**证伪**。
> 评测方法见 [memory-eval.md](memory-eval.md)。

## 1. 为什么改：旧设计的杠杆点是人

在 0.13.x 之前，笔记进入模型视野只有一条路：**人用 `@` 把笔记贴上去**（`@` 候选菜单 →
输入框 chip → 用户消息里一行引用路径 → pre-step 折进请求，见 [context.md](context.md)）。

这条路的自动化程度是零。它的天花板就是**人得想起来**：

- 人忘了 → 笔记等于不存在；
- 人记得 → 也只是把那篇的全文塞进上下文，与「把文件放进仓库让 agent 自己 `read`」相比，
  增量只有「不用污染代码仓库」和「选择更省上下文」。

更要命的对照是：dsh 一等方已经有 `@` 路径引用（`file-reference` 服务，系统提示里就教模型
「@ 是用户显式引用的路径」）、有用户级/仓库级 `AGENTS.md`（`agent-instructions`，每次会话
自动加载）、有 `session_search` 翻历史。也就是说，**旧设计的每一条承重机制都有一等方对应物**，
插件剩下的只是便利与工程，不产生新的问答能力。

结论：**只要杠杆点是「人别忘了」，它就不太可能提升问答效果。** 这不是实现质量问题，是结构问题。

## 2. 改成什么：让模型自己决定去查、去记

把笔记从「人贴的附件」改成「**agent 可调用、可写入、跨会话存活的记忆**」。三件事：

### 2.1 三个工具（已落地，`agentTools` 控制）

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `note_search` | 按关键词跨工作区搜笔记；**不传 `query` 时列出最近更新的笔记**（让模型先知道库里有什么） | 结果只带模型要的字段：工作区 / 文件名 / 标题 / 命中行。UI 用的 highlight ranges 被剥掉 |
| `note_read` | 按文件名（可省 `.md`）或**精确标题**读全文 | 文件名精确匹配优先于标题；跨工作区歧义时先用**调用会话自己的工作区**打破平局，仍歧义就**返回候选让模型问**，绝不猜 |
| `note_write` | 追加**持久事实**（用户的长期偏好、约定、环境事实、决策） | **只追加，绝不截断**；`mode: 'create'` 遇到已存在的文件直接拒绝。agent 写路径**故意不提供 overwrite**——毁掉人的笔记是最严重的失败 |

`note_write` 与 UI 写入共用同一把 `KeyedLock`，所以「AI 正在写 + 人正在保存」不会互相踩。

### 2.2 发现（已落地）

工具存在 ≠ 模型会用。一个从不看工具列表的模型永远不会调 `note_search`，于是图书馆对它隐形。
所以每次会话注入**一条**短通知（`context-inject.ts` 的 `notesNotice`）：

- **一次/会话**（不是每步）：成本是每条会话固定一小段，不是每步叠加；
- **只在工作区真的有笔记时**注入：空库不说话；
- **措辞跟随 `agentTools` 档位**：`read` 档不会去宣传一个没注册的 `note_write`。

而「**什么时候该查**」这条策略放在**工具描述**里，不是放进注入消息。理由：工具描述是唯一
每步都在模型眼前、且不额外花 token 的通道（dsh 的 `read` / `grep` 就是这么教会模型用它们的）。
per-step 注入策略会为每个 step 付费，而收益与一次会话通知几乎相同。

### 2.3 档位（`Config.agentTools`）

| 值 | 注册的工具 | 适用 |
|---|---|---|
| `'write'`（默认） | 全部三个 | 把笔记当记忆用 |
| `'read'` | `note_search` + `note_read` | 保守：agent 只能查，只有人能改笔记 |
| `'off'` | 无 | 回到纯文档管理器（旧行为），也是评测的对照组 |

非 `volatile`：这是**部署开关**，不是用户设置（理由见 [architecture.md](architecture.md) 设置一节）。

## 3. 这条路线成立的前提（也就是可能被打脸的地方）

1. **模型真的会用工具**：工具描述写得好不好，直接决定调用率。
2. **笔记里真的有「仓库里推不出来的知识」**：如果答案都能从代码/AGENTS.md 得出，工具就是噪声。
3. **写进去的东西值得跨会话留存**：agent 若往里灌临时任务状态，库会腐烂——这是 `note_write`
   描述反复强调「不要记临时状态、不要记仓库已写明的」的原因，也是下一步「人审阅」要解决的。

因此**不要靠辩论决定它的价值**，按 [memory-eval.md](memory-eval.md) 跑一次对照评测：
with/without 的答案差异 ≈ 0，就说明它在「提升问答」这根轴上确实是伪需求，那时应当
降级为文档管理器（`agentTools: 'off'`）或归档，而不是继续加功能。

## 4. 还没做（刻意留白）

- **无头 / SDK / ACP 部署下根本加载不起来**（2026-09-24 做评测自动化时实测发现）：插件的
  `inject` 依赖 `webServer`，而 `webserver` 只由 **web-app bundle** 挂载（`dsh-base` 与
  `dsh-sdk-app` 都没有）。于是「agent 记忆」在最需要它的自动化场景（SDK 驱动、CI、定时任务）
  里连插件都起不来，更别说工具。**修法明确且不复杂**：把 `webServer` 降级为**可选服务**——
  `ctx.get('webServer')` 取不到就跳过路由与 icon 注册，并在它晚到时用
  `ctx.inject(['webServer'], …)` 补注册（客户端半边已有同款晚到激活先例）。做之前要真机
  验证 web 侧不回归（刚修过一次加载期崩溃，这里动的是加载顺序，风险集中在此）。
- **策展 / 审阅**：现在 agent 写进笔记的内容直接生效，人只能在管理器里事后看到并手改。
  真正的「记忆」应当有 **provenance（哪个会话、什么时候写的）+ 待审阅队列 + 一键回滚**。
  这是与「agent 可写」配套的另一半，也是本设计里最明显的缺口（`meta.json` 目前只有
  `title` / `updatedAt`，没有写入者信息）。
- **检索质量**：现在是 token AND 子串匹配。笔记规模上来后需要排序（标题命中、时间、
  互链度数），向量检索不必需但排序必需。
- **跨工作区的个人库**：目前笔记按工作区隔离。用户的**个人**知识（跨项目偏好）没有归属，
  现在只能随便挑一个工作区放。
- **按需加载 vs 预加载**：现在 `note_search` 全库扫描并在 host 侧读文件；笔记上千后需要索引。
